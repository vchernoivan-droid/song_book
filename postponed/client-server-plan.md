# План: клиент-серверная архитектура (local-first)

Статус: отложено, согласовано в обсуждении. Код не начат.

## Цель

Local-first / offline-first с ручной синхронизацией:

- **Устройство работает автономно.** Локальная БД — источник правды для устройства: песни и плейлисты лежат локально, все операции работают без сети.
- **Сервер — общая копия** для обмена между устройствами. Ничего не диктует, хранит то, что закинули.
- **Синк — ручной, инкрементальный** push/pull плейлистов и песен.

## Модель данных (одинакова на устройстве и сервере)

```
Song          { Id Guid, Title, Author?, Album?, Content, UpdatedAt, DeletedAt? }
Playlist      { Id Guid, Name, UpdatedAt, DeletedAt? }
PlaylistSong  { PlaylistId, SongId, Position, UpdatedAt, DeletedAt? }
```

- `Id` — стабильный Guid. Сейчас песня ключуется именем файла — для синка не годится.
- `DeletedAt` — tombstone: удаление не стирает запись, а помечает. Метка доезжает всем устройствам; физическая очистка — отдельный GC после подтверждения всеми.
- `scrollSpeed` убран: фича автоскролла выпилена (в коде осталось убрать UI — отдельная задача, не часть этого плана).

Песня на сервере хранится один раз, плейлист ссылается на `SongId` — дубликатов нет.

## Идентичность и пользователи

- Пользователей нет. Устройство при первом пуше регистрируется на сервере и получает ключ (для логов/идентификации).
- При попытке закинуть на сервер спрашиваем **e-mail**. «Свободная» песня (не в плейлисте) на сервере попадает в плейлист с названием = e-mail. Один e-mail на нескольких устройствах = одна библиотека.
- Открытый вопрос: e-mail (библиотека) и ключ устройства (логи) — одна сущность или разные.

## Синхронизация: версии, base, tombstone

Инкрементальная, не снапшот. У каждой записи на сервере — `version` (целое, растёт на 1 при каждом принятом изменении). Устройство помнит `base` — версию, которую видело последней, и помечает запись «изменена после base».

**Пуш** — устройство шлёт запись + `base`. Сервер сравнивает:

```
base == текущий version?
  да  → принимает, version += 1
  нет → конфликт, возвращает серверную версию
```

**Пул** — сервер отдаёт всё, у чего `version > base`. Устройство ставит `base = version`.

Часы устройств не используем: порядок определяет сервер через монотонный `version`.

## Правила мержа

- **Плейлист** — набор песен = объединение по `SongId`: одна и та же → одна, разные → обе. Порядок сохраняется, новые в конец; если оба переупорядочивали — побеждает последний заливший (v1 — самый простой вариант).
- **Песня (контент)** — конкурентная правка не мержится автоматически: первый пушащий проходит, второй получает обе версии, сравнивает, выбирает, заливает заново (как разрешение конфликта в гите).
- **Удаления** — едут как tombstone: обычное изменение с новой `version`.

## Этап 1 — бэкенд

Каталог `server/`. Стек: ASP.NET Core Minimal API (net10.0) + EF Core + PostgreSQL.
Порт `5180`, CORS для веб-клиента. Пакет `Npgsql.EntityFrameworkCore.PostgreSQL`.

### Эндпоинты

```
Синк:
  GET  /api/sync?since=<version>   изменения после cursor + текущие версии
  POST /api/sync/push              грязные записи с base → ok/conflict + новые версии

Устройства:
  POST /api/devices                зарегистрировать устройство (→ ключ)
```

e-mail приходит с первым пушем: сервер создаёт/находит плейлист с именем e-mail и кладёт туда свободные песни.

### Файлы

`Program.cs`, `Data/SongBookDbContext.cs`, `Entities/…`, `Contracts/…` (DTO),
`Endpoints/SyncEndpoints.cs`, `Endpoints/DevicesEndpoints.cs`, миграции.

## Этап 2 — клиент (Flutter)

### Локальная БД

- **drift** — SQLite, единый слой на нативе и вебе (wasm). Заменяет `FileSongStorage`/`PrefsSongStorage`.
- Схема = серверной (Song/Playlist/PlaylistSong) + таблица sync-метаданных (`base`, dirty).

### Модели

- `Song { id, title, author, album, content }` — без `fileName`, без `preview`, без шапок, без `scrollSpeed`.
- `Playlist { id, name, songs }`.

### Инфраструктура

- `ApiClient` — baseUrl + http + обработка ошибок.
- `SyncService` — push/pull, версии, разрешение конфликтов.
- `DisplaySettingsStore` — per-song настройки + глобальный `fontSize`.
- `ApiConfig` — выбор URL окружения.

### ApiConfig

```dart
class ApiConfig {
  // flutter run --dart-define=API_BASE_URL=http://10.0.2.2:5180
  static const _override = String.fromEnvironment('API_BASE_URL');

  static String get baseUrl {
    if (_override.isNotEmpty) return _override;          // прямой URL побеждает
    if (!kIsWeb && Platform.isAndroid) {
      return 'http://10.0.2.2:5180';                     // эмулятор по умолчанию
    }
    return 'http://localhost:5180';                      // веб/десктоп
  }
}
```

| Окружение | URL |
|---|---|
| локально (веб/десктоп) | `http://localhost:5180` |
| Android-эмулятор | `http://10.0.2.2:5180` |
| физическое Android-устройство | `http://<IP-компа>:5180` (через dart-define) |
| прод | `https://api.songbook.example` (через dart-define) |

### UI

- **Главный экран** — локальные песни + плейлисты; поиск по названию/автору/альбому/тексту.
- **Плейлист** — упорядоченный список песен; добавить/убрать/переупорядочить.
- **Песня** — просмотр + редактирование (название/автор/альбом/текст), сохранение локально.
- **Синк** — кнопка push/pull; при первом пуше спрашиваем e-mail; при конфликте — экран «моя vs серверная».
