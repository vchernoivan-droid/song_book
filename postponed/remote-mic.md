# План: микрофон на другом устройстве (слушаем на телефоне, скроллим на компе)

Статус: реализовано и обкатано (ноябрь 2026). Отступления от плана: `localeId` nullable — `localeIdFor` даёт `null` для нейтрального текста, телефон слушает системной локалью; `listen` шлётся в начале отсчёта 3-2-1 (STT телефона прогревается до пения), при переподключении телефона посреди песни — в начале автоотсчёта.

Грабли Android STT (обкатано на живом телефоне):

- dictation-сессия умирает молча после `finalResult`: ни `notListening`, ни `done`, ни error — рестарт только по статусам не ловится; триггерим рестарт по самому `final` и по статусам (оба через `stop` → `listen`, 150–300 мс);
- `pauseFor` в `SpeechListenOptions` прокидывается в `EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS` — растягивает endpointer: сессия переживает паузы между фразами, финал на конце фразы больше не приезжает, контекст копится непрерывно; 10 с — рабочее значение, оно же dart-автостоп по тишине (страховка на проигрыши);
- гудки старта/стопа — системные, у сетевого распознавателя не отключаются; проверен `onDevice: true` (`EXTRA_PREFER_OFFLINE`) — гудков нет, сессии ~80 с, качество чуть ниже сетевого, но локатор справляется; принят как дефолт, возможный тумблер «качество / без гудков» — в отложке;
- `listen()` может молча не подняться (после убийства приложения посреди stop→listen): без исключений, но нет `status: listening`, нет партиалов и уровней — слова не приходят вовсе. Лечится вотчдогом старта: 3 с без `listening` → `cancel` + повтор, со 2-й попытки + полный `initialize()`, после 3 — error на сервер и статус на телефоне;
- диагностика: ин-мемори лог (кольцо на 500 строк, все события/статусы/partials) + кнопка «Отправить лог» + `POST /log` на маке, пишет рядом с STT-логами.

## Реплей логов

`ReplayHeardFeed` ест список `HeardEvent` целиком — синтетика и тесты. Реплей
реальных логов телефона ограничен: в лог пишется хвост 60 символов
стиченного текста, полный сырой текст сессии не сохраняется — замкнуть
можно только строки без подклейки. Для точного реплея надо писать полный
текст сессии (строка станет длинной) или отдельным файлом.

## Задача

Разнести фичу автоскролла по пению на два устройства:

- **телефон** (у каждого в кармане, микрофон хороший) — слушает пение, гоняет STT;
- **комп/проектор** (экран без микрофона) — крутит скролл к строке, которую поют.

## Почему так устроено

- `speech_to_text` официально поддерживает только **android/ios** (проверено в
  `pubspec.yaml` пакета в pub-cache). На десктопе локальный микрофон в принципе
  не заведётся → для компа «принимать с телефона» не опция, а основной путь.
- Локальный микрофон **не убираем** — на мобильных он работает; остаётся
  кнопкой «Автоскролл». На десктопе кнопку тоже **не прячем**: у десктопов
  бывают микрофоны, «пожмём, поглядим» (STT, скорее всего, ответит
  «Микрофон недоступен» — это ок).
- Шов в коде уже готовый: всё, что после `onResult`, не знает, откуда взялись
  слова.

```
микрофон (SpeechToText)
   → SongListenLogger.onResult(words)
   → SongDetailScreen._onRecognized(words)
   → LyricLocator.locate(...)   // → номер строки
   → _singerLine + pursuit → ScrollController
```

Меняется только источник слов: вместо локального STT — слова из сети.

## Роли

- **Комп (сервер + экран + мозг).** Поднимает WebSocket, принимает слова,
  гоняет их через существующий `_onRecognized` → `LyricLocator` → скролл.
  Матчит против **своей** раскладки (`fontSize`, транспонирование,
  `renderSongLines`), поэтому номер строки всегда сходится.
- **Телефон (клиент = беспроводной микрофон).** STT, пересылка хвоста слов.
  Песню не знает, локатор не запускает.

Если бы телефон считал номер строки сам — понадобилась бы та же песня с той
же раскладкой на обоих устройствах. Хрупко, поэтому шлём слова, не строки.

## Протокол (JSON, `dart:convert`, без новых сетевых зависимостей)

Парадигма: телефон — просто микрофон, управление только на компе.

- сервер → клиент `{"type":"hello","v":1}` — версия протокола; при мисматче
  телефон показывает «обновите приложение».
- клиент → сервер `{"type":"ready"}` — `SpeechToText` инициализирован,
  разрешение на микрофон получено; комп после него начинает отсчёт.
- сервер → клиент `{"type":"listen","localeId":"ru-RU"}` — начинай слушать на
  этом языке, с чистого листа (сброс накопленного текста). Шлётся на старт
  песни и при смене песни; локаль берётся из текущего текста
  (`SongListenLogger.localeIdFor`), поэтому может меняться от песни к песне.
- клиент → сервер `{"type":"words","text":"..."}` — хвост последних ~32 слов
  накопленного текста. Локатору нужны только последние 8 ключей, ~32 — запас
  на выпавшие/пустые слова. Порядок: телефон режет хвост по словам → шлёт;
  комп делает `keysOf` по короткому входу → хвост 8 → матчит (как сейчас).
- сервер → клиент `{"type":"stop"}` — выключи микрофон. Соединение остаётся:
  для следующей песни комп пришлёт `listen` заново, телефон не сканирует QR
  повторно.
- клиент → сервер `{"type":"error","message":"..."}` — STT не завёлся /
  микрофон не дали, показать на компе.
- сервер → клиент `{"type":"rejected"}` — «кто первый тот и папа»: экран уже
  занят другим телефоном, это соединение закрывается.

Таймлайн: `connect → hello → ready → (отсчёт) → listen → words… → stop`
(и `listen` снова для следующей песни).

Кнопка «Отключиться» на телефоне не имеет сообщения в протоколе: она просто
закрывает сокет. Комп видит разрыв на серверной стороне — `onDone` (чистое
закрытие) или `onError` (обрыв) — и останавливает автоскролл. Чтобы мёртвый
телефон (смахнули приложение, пропал Wi-Fi) отвалился за секунды, а не по
долгому TCP-таймауту, на серверном WebSocket выставляем `pingInterval`
(~5 секунд).

Порт эфемерный (`HttpServer.bind(anyIPv4, 0)`).

## Зависимости (QR)

- `qr_flutter ^4.1.0` — генерация QR на компе (pure Dart, рисуется везде,
  включая десктоп).
- `mobile_scanner ^7.4.2` — скан на телефоне; поддерживает Android/iOS/macOS/web
  (macOS = тестовый стенд, раз пока тестируем на лэптопе).
- WebSocket/JSON — `dart:io` + `dart:convert`, новых зависимостей нет.

Разрешения платформ:

- Android: `RECORD_AUDIO` (уже есть для STT), `CAMERA` (скан), `INTERNET`.
- iOS: `NSMicrophoneUsageDescription`, `NSSpeechRecognitionUsageDescription`
  (уже есть), `NSCameraUsageDescription` (скан).
- macOS: `NSCameraUsageDescription` + `com.apple.security.device.camera`
  (скан) + `com.apple.security.network.server = true` (входящие
  WebSocket-соединения) — оба entitlement в `DebugProfile.entitlements` и
  `Release.entitlements`; плюс запрос на входящие соединения от файрвола.

## Выбор IP для QR (вариант B)

На маке `NetworkInterface.list()` отдаёт все интерфейсы: `en0` (Wi-Fi),
`utun*` (VPN), `awdl0` (AirDrop, `169.254.*`), `vmnet*` (Docker/VM),
`lo0`. Комп заранее не знает, в какой подсети сидит телефон, поэтому не
выбираем один адрес — кладём в QR **все** кандидаты, телефон пробует по
очереди.

Формат QR: `{"port":54321,"ips":["192.168.1.23","192.168.40.1",...]}`.
Порт один — сервер висит на всех интерфейсах. Телефон строит `ws://ip:port`
и пробует по порядку с таймаутом 1.5–2 с на кандидата; первый живой —
победил. Никакого ручного подбора.

Подготовка списка (только для порядка попыток, не для единственного выбора):

- убрать loopback (`includeLoopback: false`) и link-local
  (`includeLinkLocal: false` у `NetworkInterface.list`);
- сортировка: физические интерфейсы первыми (`en*`), туннели/виртуальные
  в конец (`utun*`, `vmnet*`, `tap*`, `bridge*`);
- в конце — приватные диапазоны (`192.168.*`, `10.*`, `172.16–31.*`) раньше
  прочих.

Рядом с QR на компе всё равно показываем список адресов текстом (отладка /
ручной ввод).

Позже (не сейчас) можно mDNS/UDP-обнаружение, чтобы убрать QR целиком.

## UX

- **Комп.** Тап «Микрофон на другом устройстве» → в нижней панели QR со
  всеми адресами (порт + список) + «ожидание телефона» + список адресов
  текстом для отладки/ручного ввода. Подключился → отсчёт 3-2-1 → поехали.
  Отключение — та же кнопка. Телефон отключился → стоп автоскролла +
  «Телефон отключился».
- **Телефон.** FAB → `RemoteMicScreen` → наводит камеру на QR (или вводит адрес
  руками) → «Подключить» → слушает и шлёт. «Отключиться» в один тап; если
  сервер закрыл сокет — телефон сам выключает микрофон.

## Тесты

- `test/remote_song_listener_test.dart` — unit без виджетов: старт сервера →
  WS-клиент подключается, сервер шлёт `hello`; клиент шлёт `ready` → сервер
  шлёт `listen`; клиент шлёт `words` → `onResult`; второе соединение →
  `rejected` и закрыто; разрыв → `onPeerDisconnected`.
- `test/song_detail_screen_test.dart` — добавить фейк `remoteListenerFactory` и
  сценарий «подключился → отсчёт → слова → скролл поехал».

## Отложено

- `SongLogSink` (общий лог-файл для калибровки `LyricLocator`): на старте
  скипаем, remote пишет в `debugPrint`. Вернёмся отдельным шагом.

## Не делаем (пока)

- Несколько певцов/хор.
- Web-сборка в роли сервера (в браузере `dart:io` нет, входящие соединения
  не поднять).
- Шифрование/авторизация (доверенная локальная сеть).
- Фиксированный порт, облако/интернет.
- Удалённое управление с телефона: `pause`/`resume`, `state`, `goto`
  («перенести стрелку») — телефон остаётся просто микрофоном, это отдельная
  будущая тема.

## Оговорки реального мира

- Оба устройства в одной Wi-Fi; на гостевых сетях бывает AP-isolation — тогда
  телефон компа не увидит.
- macOS/Windows могут спросить разрешение на входящие соединения при первом
  запуске.
